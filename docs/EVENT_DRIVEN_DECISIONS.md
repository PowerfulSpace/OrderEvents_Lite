# Когда применять event-driven

Event-driven — не серебряная пуля. Это инструмент для конкретных ситуаций, и у него есть цена. Прежде чем вводить событие, стоит ответить на вопрос «стоит ли», а не только «как это работает». Как устроен пайплайн — в [ARCHITECTURE.md](ARCHITECTURE.md); почему приняты текущие решения — в [DECISIONS.md](DECISIONS.md); что упрощено — в [KNOWN_SIMPLIFICATIONS.md](../KNOWN_SIMPLIFICATIONS.md); куда расти — в [PRODUCTION_ROADMAP.md](PRODUCTION_ROADMAP.md).

Стоимость event-driven складывается из трёх частей. Сложность: очередь, воркер, eventual consistency, отладка, дубли, порядок сообщений. Инфраструктура: хранилище для outbox, внешняя шина, если выходим за процесс. Операционка: наблюдаемость, retry, dead-letter. Если выгода не перекрывает эти затраты, прямой вызов метода будет проще и надёжнее.

Ниже — критерии «да» и «нет», различие domain и integration событий, чек-лист, кейсы и типичные ошибки. Это мышление и критерии, а не инструкция по настройке конкретной шины.

## 1. Когда событие оправдано

- **Несколько независимых реакций на одно изменение.** Лог, уведомление, аналитика, склад — каждому нужно одно и то же изменение, но домен не должен знать, кто реагирует. Пример: создание заказа порождает запись в аудит, сообщение в Telegram и событие для внешней системы.

- **Побочный эффект не должен блокировать основной сценарий.** Клиент не ждёт Telegram или письма, а получает ответ после коммита. Пример: `POST /orders` возвращает `201` за ~300 мс, уведомление уходит в фоне.

- **Медленный или ненадёжный внешний вызов.** HTTP к стороннему API нельзя держать внутри транзакции: он может зависнуть или упасть. Пример: отправка уведомления в Telegram через внешний сервис.

- **Ослабление связности.** Домен не знает про подписчиков, добавление новой реакции не меняет `Order.Create()`. Пример: новый хендлер аналитики добавляется без правок агрегата.

- **Асинхронность по природе.** «Когда-нибудь обработается» — приемлемо. Пример: email-рассылка, построение отчёта, фоновая синхронизация.

- **Аудит и история изменений.** Событие — это факт «что произошло», его можно логировать и воспроизводить. Пример: журнал смены статусов заказа.

## 2. Когда событие не нужно

- **Одна реакция, синхронно, мгновенно.** Прямой вызов метода проще и понятнее. Пример: после изменения поля сразу пересчитать производное значение в том же обработчике.

- **Нужна строгая консистентность «здесь и сейчас».** Баланс, резерв, списание денег — это транзакция, а событие даст лишь eventual consistency. Пример: оплата, которая должна быть атомарна с изменением заказа.

- **Маленький CRUD.** Событий одна-две, подписчиков нет, оверхед без выгоды. Пример: справочник товаров с полями и обычными CRUD-операциями.

- **«На всякий случай» / «может пригодится».** Событие без подписчиков — мёртвый код плюс сложность. Пример: событие на каждое сохранение сущности, которое никто не слушает.

- **Замена прямому вызову ради «модно».** Если реакция одна и в том же процессе, событие только добавит слоёв. Пример: один хендлер, который делает то, что можно вызвать напрямую.

- **Событие как команда.** Повелительное `SendEmail`, `ChargePayment` — это не факт, а указание; смешение фактов и команд путает. Пример: событие, которое требует выполнить действие, а не сообщает о свершившемся.

## 3. Domain event vs Integration event

Domain event живёт внутри процесса и границы домена: это факт о произошедшем изменении, передаётся in-process (в этом проекте — `INotification`) синхронно или через локальную очередь. Integration event пересекает границу сервиса: это контракт между системами, доставляемый внешней шиной (RabbitMQ/Kafka) с гарантией at-least-once, версионированием контракта и обязательной идемпотентностью на принимающей стороне.

| Критерий | Domain event | Integration event |
|----------|--------------|-------------------|
| Граница | внутри процесса/домена | между сервисами/системами |
| Транспорт | in-process (`INotification`), локальная очередь | внешняя шина (RabbitMQ/Kafka) |
| Гарантии доставки | в рамках процесса, без сетевых гарантий | at-least-once, возможны дубли |
| Контракт | внутренний, меняется свободно | публичный, требует версионирования |
| Идемпотентность | желательна | обязательна |
| Пример | `OrderCreated` → лог + Telegram | `OrderCreated` → склад/оплата в другом сервисе |

## 4. Чек-лист «нужно ли событие»

- **Есть ли больше одной реакции на изменение?** Да → событие уместно. Нет → вероятно, хватит прямого вызова.
- **Может ли реакция быть отложенной (клиент не ждёт)?** Да → событие подходит. Нет → нужен синхронный путь.
- **Есть ли медленный или ненадёжный внешний вызов?** Да → событие снимет его из транзакции. Нет → можно обойтись напрямую.
- **Готов ли я к eventual consistency (данные не сразу)?** Да → событие допустимо. Нет → нужна транзакция.
- **Готов ли я к дублям и порядку (идемпотентность, outbox)?** Да → можно двигаться. Нет → сначала закрыть эти вопросы.
- **Есть ли наблюдаемость (логи, метрики, трейсы)?** Да → событие можно отлаживать. Нет → сначала наблюдаемость.
- **Не пытаюсь ли я заменить прямой вызов «потому что модно»?** Да → событие не нужно. Нет → решение обосновано.
- **Это факт (прошлое) или команда (повелительное)?** Факт → событие. Команда → прямой вызов/команда.

## 5. Примеры на кейсах

- **CRUD-справочник (`Product` с полями).** Не событие: одна реакция, синхронно, нужна строгая консистентность.

- **Создание заказа + уведомление.** Событие: уведомление не блокирует ответ, домен не знает про Telegram; заказ уже в БД — уведомление может упасть, данные целы.

- **Оплата.** Не событие для «списать деньги»: строгая консистентность и транзакция. Событие — для «после успешной оплаты уведомить/обновить склад», то есть для побочных эффектов.

- **Аудит изменений.** Событие: это факт, подписчиков несколько, обработку можно отложить.

- **Синхронизация с внешней системой (1С, склад).** Integration event: пересекает границу сервиса, at-least-once, нужна идемпотентность.

- **Аналитика и метрики.** Событие: отложенно, не блокирует основной сценарий, домен не знает про подписчиков.

- **Смена статуса заказа.** Событие, если есть подписчики (лог, уведомление, склад). Не событие, если это только запись в БД и больше ничего.

## 6. Типичные ошибки

- Событие на каждое изменение «на всякий случай» — мёртвый код и лишняя сложность.
- Событие как команда (`SendEmail` вместо `OrderCreated`) — смешение факта и указания.
- Событие для строгой консистентности (оплата, резерв) — eventual consistency здесь не подходит.
- Забыли про идемпотентность при переходе на шину — получили дубли.
- Нет наблюдаемости — отладка event-driven без логов и трейсов болезненна.
- Событие без подписчиков — зачем оно нужно?

## 7. Связь с этим проектом

В OrderEvents_Lite `OrderCreated` оправдан: у него несколько реакций (`OrderCreatedHandler`, `TelegramOrderCreatedHandler`), уведомление не блокирует ответ, а Telegram может упасть. `OrderStatusChanged` — событие, потому что есть подписчик (лог); если подписчиков не останется, событие станет лишним.
